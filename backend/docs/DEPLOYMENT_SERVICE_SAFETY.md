# حماية اختيار خدمة النشر

إعادة النشر لا تعتمد على الاسم وحده. قبل تحديث أي متغير أو إرسال طلب نشر، يجب أن تطابق الخدمة المستودع والفرع ونوع Web Service وبيئة Node ومجلد التشغيل الجذري. إذا ضُبط RENDER_OWNER_ID تُطابق مساحة العمل أيضاً. غياب البيانات اللازمة أو فشل البحث أو تكرار الاسم يوقف العملية دون إنشاء خدمة بديلة أو إرسال أسرار.

تُحدّث المتغيرات المرسلة مفتاحاً بمفتاح. طلب PUT الجماعي السابق كان يحذف المتغيرات غير الموجودة في الطلب؛ راجع [توثيق التحديث الجماعي](https://api-docs.render.com/reference/update-env-vars-for-service) و[تحديث متغير واحد](https://api-docs.render.com/reference/update-env-var).

فشل تحديث أي متغير يوقف طلب النشر ويُبلغ بأن بعض المتغيرات قد حُفظت؛ التحديث متعدد المفاتيح ليس معاملة ذرية. لا توجد إعادة تلقائية عمياء بعد رد مبهم. يمكن إعادة المحاولة بعد مراجعة الخدمة. فشل طلب النشر نفسه يعيد خطأ، وليس نجاحاً.

تغييرات المتغيرات تحتاج طلب نشر صريح حسب عقد Render. عندما لا تتغير متغيرات والخدمة تنشر تلقائياً، لا يُرسل طلب إضافي يكرر نشر الدفعة. نجاح API يعني قبول الطلب؛ استجابة التطبيق تسمي الحالة requested ولا تثبت أن النسخة أصبحت live.

عند إنشاء خدمة جديدة دون RENDER_OWNER_ID، لا يُختار أول مالك من عدة مساحات. يسمح الاكتشاف التلقائي بنتيجة واحدة فقط، وإلا يتوقف برسالة تطلب تحديد مساحة المشروع.

التحقق: اختبارات محقونة لا تتصل بـ Render، تغطي اختلاف المستودع والفرع والمجلد ونوع الخدمة والمساحة، أخطاء البحث، تحديث المتغيرات، رفض النشر، ومنع الطلب المكرر. لا تغير هذه الدفعة اكتشاف Next/fullstack أو إعداد خوادمه.
