## 📍 نقطة البداية (2026-09-02)

طلب المالك مناقشة خطة معمارية جاءت من محادثة ChatGPT خارجية (ملخّصها في
سياق الجلسة) تشخّص JAOLA OS كـ"عضلات كثيرة بلا عمود فقري موحّد" وتقترح
خطة ١٠ مراحل (تجميد → قفل معماري → Core Kernel → استخراج JCR → طابور
مهمات دائم → Model Router → Verification → Plugin Runtime 2.0 → Mission
Control → Self-Improvement).

**قرار النطاق**: الـbackend فعلياً 241 ملفاً و53,033 سطراً — فحصه كاملاً
(Phase 0 الكاملة من الخطة الأصلية) عملٌ ضخم لا يناسب جلسة واحدة. النطاق
المتفق عليه: **مسارات التنفيذ الفعلية فقط** — من يستدعي من، فعلياً، في
مسار تشغيل الوكلاء (agent execution) — لا مسحٌ شامل لكل الملفات.

## 🔴 تصحيحٌ جوهري: لا يوجد "مساران متنافسان" — يوجد كودٌ ميت + مسار واحد فعلي

الوثيقة الأصلية صوّرت `agentOrchestrator.js` مقابل `PluginOrchestrator.js`
كمسارين مستقلين لتنفيذ الوكلاء يجب "توحيدهما" — هذا **غير دقيق** بعد
التحقق الفعلي:

### 1) `backend/services/agentOrchestrator.js` — **كودٌ ميتٌ تماماً، لا "مسارٌ ثانٍ"**
```
$ grep -rn "agentOrchestrator" --include="*.js" backend/ | grep -v node_modules
# نتيجة: صفر — لا ملف واحد يستورده أو يستدعيه
$ git log --oneline --follow -- backend/services/agentOrchestrator.js
8a272c1 إصلاح: 404 عند تحديث الصفحة على مواقع المستخدمين ذات توجيه SPA (#299)
# commit واحد فقط في تاريخه كله، وهو غير متعلق بمحتواه (لمسة جماعية عابرة)
```
25 سطراً، بلا أي مستدعٍ، ملفٌّ سقط من مسار تنفيذ حقيقي (أو كان بداية
تجربة لم تُكمَل). **الإجراء الصحيح: حذفٌ مباشر لا "توحيد" — لا شيء
يعتمد عليه فيُكسَر.**

### 2) المسار الفعلي الوحيد لتنفيذ الوكلاء (مُتتبَّعٌ سطراً بسطر)

```
POST /api/chat  (server.js:1953)
  └─ يبني حرفياً كائن `agents` (server.js:~1961) من استيرادات دوال مباشرة
     (coreClassifyIntent, coreGenerateCodePlan, coreEditCodePlan,
      architectReview, qaVerify, deployProject, applyTemplate, ...)
  └─ runtime.handleUserMessage(null, {...}, agents, dbStatus)  (server.js:1992)
     [runtime = new JaolaCognitiveRuntime(io) — نسخة واحدة، server.js:266]
       └─ [داخل jcr.js] تصنيف نيّة عبر ceoBrain.js (classifyIntentFast/decide/...)
       └─ executeMission | surgicalEdit | runExecutiveBrain | runDynamicMultiAgentRuntime
          (jcr.js — كل الفروع تستقبل نفس كائن `agents` المُمرَّر من server.js
           كوسيطة، لا عبر أي registry مستقل)
       └─ missionQueue.js + stateMachine.js: حالة/طابور **داخليان لنفس
          المسار** — server.js يقرأ منهما فقط للعرض (queueStatus،
          getProjectSummary)، لا يقودهما بمسارٍ مستقل.
       └─ orchestrator.runHook('beforeBuild'/'afterBuild')  [PluginOrchestrator]
          — hooks دورة حياة الإضافات الخارجية حول البناء فقط، لا اختيار
          "أي وكيل يُنفَّذ" للمسار الأساسي.
```

**الخلاصة**: المسار الحيّ الوحيد لتنفيذ مهمة مستخدم هو `/api/chat` →
`JCR.handleUserMessage` → تفويضٌ داخلي بوسيطة `agents` — **مسارٌ واحدٌ
متماسك فعلاً، لا اثنان متصارعان**. المشكلة الحقيقية ليست "تعدد أنظمة
تنفيذ" بل أن **كل هذا المسار مكدّسٌ داخل صفٍّ واحد (jcr.js) بـ3059 سطراً**
— وهذا فرقٌ جوهري في التشخيص يغيّر الخطوة الأولى الصحيحة.

### 3) `PluginOrchestrator.js` — نظامٌ حقيقيٌّ ومستقلٌّ **عن قصد**، لا بالخطأ

مسؤوليته: تحميل إضافات (plugins) خارجية من القرص (`backend/plugins/`)،
تشغيل hooks دورة حياتها، وتسجيل **وكلاء الإضافات فقط** (لا الوكلاء
الأساسيين السبعة). له مستهلكان حقيقيان مختلفان تماماً عن `/api/chat`:
- `POST /api/admin/agents/:name/run` (server.js:2599) — **مسار اختبار
  إداري صريح** ("🧪 تجربة وكيل مباشرة من اللوحة")، محصور بالأدمن، غير
  متاح للمستخدم العادي إطلاقاً.
- `beforeBuild`/`afterBuild` hooks داخل مسار `/api/chat` نفسه (أعلاه) —
  توسيعٌ لا بديل.

**لا حاجة لـ"توحيده" مع مسار `/api/chat`** — فصله عن الوكلاء الأساسيين
تصميمٌ سليم (إضافات الطرف الثالث معزولة عن الوكلاء الجوهريين)، والوثيقة
الأصلية أخطأت بتصنيفه "مساراً متنافساً".

## 🎯 الخطوة الأولى المقترحة (بدل الخطة الكاملة ١٠ مراحل)

1. **حذف `backend/services/agentOrchestrator.js`** — تنظيفٌ بلا مخاطر
   (صفر مستدعين، مؤكَّدٌ بالبحث والتاريخ أعلاه). أول التزامٍ فعلي وملموس
   من هذا الملف، بلا انتظار أي "تجميد" أو "قفل معماري" شامل.
2. **توثيق هذا الرسم كمصدر حقيقة** (هذا الملف) — أي عمل مستقبلي على
   `jcr.js` أو `PluginOrchestrator.js` يبدأ من هنا لا من افتراضٍ جديد.
3. ⏳ **لم يُفحَص بعد** (خارج النطاق المتفق عليه اليوم): تفاصيل ما بداخل
   `runExecutiveBrain`/`runDynamicMultiAgentRuntime` سطراً بسطر، وما إذا
   كانت `missionQueue`/`stateMachine` تحملان أي منطقاً يستحق استخراجاً
   مستقلاً (المفتاح الحالي `username:project` بدل `missionId` — ادّعاءٌ
   من الوثيقة الأصلية لم يُتحقَّق منه بعد هنا).
